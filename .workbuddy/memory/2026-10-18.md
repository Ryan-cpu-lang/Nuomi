## 补记（定位并修复不确定性内存 bug + NUC 工具链真机验证）

### A. 引用计数结构性缺陷（根因已定位并修复）
- 用 `-DMOCHI_DEBUG` 存活集合 + 分配序号 + 阶段标记精确定位：崩溃点在 `runFile-release-form` 释放 form 的 AST 时，撞上已被过度释放的 intern 符号（如 `xs`）→ use-after-free。
- **根因**：链表/向量节点创建时**未 retain 其持有的共享对象**（car / 向量元素），但 `freeObject` 释放这些节点时却 `release(car)`/`release(items)`。被多处 AST 共享的 intern 符号因此被多减引用计数 → 提前 free → 后续访问 UAF。连跑才偶发正是因为复用/释放顺序依赖堆状态。
- **修复**（节点创建处补 retain，所有权清晰化）：
  - `reader.c` readList：`cell->car = forms[i]; retain(forms[i]);`（链表 car 是共享对象）；向量分支 `retain(forms[i])`。
  - `native.c`：
    - `natCons`：对 `a[0]`、`a[1]` 都 `retain`（参数由调用方 argv 持有，apply 返回后会被 release，cell 要长期持有必须自留）。
    - `natList`：对 `a[i]`（car）`retain`；cdr=head 用「转移所有权」不额外 retain（避免尾节点泄漏）。
    - `natVec`：对每个 `a[i]` `retain`（原“转移所有权”写法会让向量内指针在 argv 被 release 后悬空）。
  - `eval.c` evalSet：先 `retain(val)` 再 `release(*slot)` 再存槽再 `release(val)`，防 `(set! xs (cdr xs))` 级联释放新值。
  - `reader.c` quote 展开：`cell1`/`q` 改用「转移所有权」不再多余 retain（修掉原本的引用泄漏）。
- **所有权规则（写代码时务必遵守）**：`evalListNode` 拥有 `argv` 并在 `apply` 返回后 `release(argv[k])`；原生函数若要把参数存进返回的容器，必须 `retain` 该参数。`allocObj` 返回 refcount=1（调用方立即获得1份所有权）；挂到别处时用 retain 追加，链后继用转移。
- 修正 `g_dbg_phase`：从 `#ifdef MOCHI_DEBUG` 内移到外部（始终声明 + 在 value.c 始终定义），使发布版也能编译（原先发布版因 `g_dbg_phase` 未声明而编译失败）。`#ifdef MOCHI_DEBUG` 仅圈住「存活集合 / dbgCheckLive / 大量 fprintf 调试桩」，发布版零开销。

### C. NUC 工具链真机验证（之前卡住的根因也修了）
- 之前 `nucutil.exe` 在 Windows 上跑不起来（bash 报 127，实为加载/运行崩溃）。两层问题：
  1. TCC 编带 `windows.h` 的程序需显式 `-lkernel32`（VirtualAlloc 等导入），否则 PE 加载失败。编译命令加 `-lkernel32`。
  2. **真正的崩溃是 `nucfmt.c` 的双重释放**：`nuc_builder_build` 末尾 `free(b->seg_data[i])`，而 `nuc_builder_free` 又 `free(b->seg_data[i])` 一次 → STATUS_HEAP_CORRUPTION（0xC0000374）。build 已把段字节深拷贝进 out，seg_data 应由 nuc_builder_free 独占释放，故删掉 build 里的那次 free。
- 修复后真机流水线全通：
  - `emit-demo demo.nuc` → wrote 4107 bytes
  - `validate demo.nuc` → `[0] valid NUC V1.0`
  - `dump demo.nuc` → 头部/段表/符号表/重定位表结构正确
  - `run demo.nuc` → `entry returned: 42 (0x2A)` ✅（验证了 VirtualAlloc 映射 TEXT + PC32 重定位 + 执行入口的宿主加载路径）
- 注意：`dump` 在 PowerShell 捕获里 `\n` 显示为 `X`（控制台代码页问题），文件内容本身正确，非功能性 bug。

## 补记 2：后端路线 A 落地（里程碑 1 — 整数算术子集 → x86_64 → .nuc）

用户拍板走 **路线 A（直接编译机器码）**，ISO 暂不碰。已实现并验证「垂直切片」：Mochi 源码 → 解析 → x86_64 代码生成 → NUC 文件 → 宿主加载执行并返回值。

### 新增文件
- `include/codegen.h` / `src/codegen.c`：Mochi→NUC 的 x86_64 代码生成器（里程碑 1 仅整数算术子集：整数字面量、`(+ - *)` 可嵌套多目、`(define name expr)` 常量折叠登记编译期符号表）。入口表达式编译成机器码 + `ret`，结果留 RAX；无外部符号、无需重定位。
- `src/main.c`：加 `-c/--compile <in.mochi> -o <out.nuc>` 编译模式（其余行为不变）。
- `samples/compile-demo.mochi`：里程碑 1 编译样例 `(define a 6)(define b 7)(+ (* a b) 100)` → 142。

### 关键实现点（手搓 x86_64 编码的坑，已踩平）
- **只用调用方保存寄存器 RAX/RDX/RCX**，绝不动 RBX/RBP/R12-R15（被调用方保存；本入口是叶子函数，clobber 会破坏 SysV ABI）。
- **左操作数用栈暂存（push rax / pop rdx）**，而非寄存器——否则嵌套算术里内层表达式会踩掉外层保存的左值（第一版就栽在这，导致 `(- (* 10 10) (* 3 3))` 算错）。
- **双操作数 `imul r, r/m` 的 Reg 字段是「目的」**（与 add/mov 相反！），`imul eax, edx` 正确编码为 `0F AF C2`，写成 D0 会变成 `imul edx, eax` 留 eax 不变（导致 `(* a b)` 返回 b）。已修正。
- 减法 `left - right` 用 `neg eax; add eax, edx` 实现（避免再借第 3 寄存器）。
- 段布局/读写复用现有 `nucfmt.c` 的 builder（所以 mochi.exe 现在也链了 nucfmt.c）。
